# Analysis — Phase 1

Step 3 of the SPDD flow. Covers the Phase 1 stories: [001](../stories/001-twenty-second-scan.md),
[002](../stories/002-case-study-deep-dive.md), [003](../stories/003-get-in-touch.md) and
[006](../stories/006-public-profile-export.md). Inputs: the stories, the approved mockups
([design.md](../design.md)), `cv-manager/profile.md`, and the conventions of the other
repositories in the account.

Decisions that needed a human call are marked **✅ Decision** with the date they were settled. Everything else is a
recommendation the canvases will adopt unless challenged.

## 1. Starting point

- **Greenfield.** The repository holds only `spdd/` and the source photo. There is no code
  to reuse, and nothing to migrate.
- **Host has neither Node nor Python.** Docker Desktop is the only runtime, so every
  command (dev server, build, export, tests) runs in a container. Task shortcuts go in a
  `.ps1` script, not a Makefile.
- **Content already exists, in two shapes.** Facts live in `cv-manager/profile.md`
  (Markdown, private, local-only). Editorial copy — headline, metrics wording, case
  studies, principles — lives in the approved Figma file and was never in `profile.md`.
- **Target host is GitHub Pages**, which serves static files only. Nothing in Phase 1
  needs a server.

## 2. Domain concepts

| Concept      | Source of truth           | Notes |
| ------------ | ------------------------- | ----- |
| Contact      | `profile.md` via export   | Email, LinkedIn, GitHub, city. Never the phone. |
| Role         | `profile.md` via export   | Title, organisation, period, location, one-line summary. Feeds the timeline. |
| Proof metric | Site content              | Value, caption, source label. Wording already passed the confidentiality check. |
| Case study   | Site content, per locale  | Problem → approach → result, role, stack, before/after pair. Long-form Markdown. |
| Repository   | Site content              | Name, pitch, honest note, stack, URL. |
| Principle    | Site content, per locale  | Numeral, title, one sentence. |
| Locale       | Site config               | `en` (default, no prefix), `es`, `it` (Phase 3). |
| UI string    | Site content, per locale  | Every label and button text; nothing hard-coded in components. |

The split matters: **facts come from `cv-manager`, persuasion lives in the site.** The export
never has to understand marketing copy, and the site never duplicates a date or a title.

## 3. Direction

### Stack

| Concern      | Choice | Why |
| ------------ | ------ | --- |
| Framework    | Astro 7, static output | Zero JavaScript by default; built-in i18n routing, content collections and image pipeline. |
| Interactivity | Plain TypeScript scripts and the `motion` library | Phase 1 needs a copy-to-clipboard, count-ups, reveal-on-scroll and a command palette. No UI framework earns its weight here; React arrives with the chat in Phase 2, as an island. |
| Styling      | Tailwind CSS 4 with the Figma tokens in `@theme` | Tokens become CSS custom properties, with light mode as a second set under `prefers-color-scheme`. |
| Fonts        | Self-hosted Geist, Geist Mono and Instrument Serif (Fontsource) | Loading Google Fonts from Google's CDN has been ruled a GDPR breach in Germany. Self-hosting also removes a DNS lookup from the critical path. |
| Images       | `astro:assets` | The portrait becomes AVIF/WebP at 1× and 2×, preloaded, as the LCP element on desktop. |
| Deploy       | GitHub Actions + `withastro/action` → GitHub Pages | Push to `main`, deploy. No secrets needed. |
| Tests        | Vitest for the export and formatters; Lighthouse CI on the built site | Happy-path only, per the account's conventions; Lighthouse enforces the performance and accessibility bars in the definition of done. |

### Proposed layout

```
astro.config.mjs
compose.yaml              dev · build · export · test services (node:22)
tasks.ps1                 dev, build, export, test shortcuts
data/public-profile.json  generated by the export, committed
scripts/export-profile.ts
src/
  content.config.ts
  content/
    cases/{en,es,it}/*.md
    site/{en,es,it}.yaml  metrics, repos, principles, hero copy
  i18n/                   UI strings and Intl formatters per locale
  styles/tokens.css       the Figma variables, dark and light
  components/             Button, StatusChip, StackTag, MetricTile, CaseCard, CommandPrompt, ContactBar
  sections/               Nav, Hero, Proof, Work, OpenSource, Experience, Principles, Contact
  pages/                  index, [locale]/index, work/[slug], [locale]/work/[slug], cv
public/cv/                generated PDFs
spdd/
.github/workflows/deploy.yml
```

Each Figma component maps one-to-one to an Astro component of the same name, so the
canvases can cite a Figma node for every file.

### Per story

**001 — Twenty-second scan.** Everything in the fold is static HTML, with no client
JavaScript on the critical path. The portrait is the desktop LCP element: preload it and
size it explicitly. On mobile the LCP is the headline text, so fonts use `font-display: swap`
with a matched fallback to avoid layout shift. The three proof rows and the sticky contact
bar match the 844px fold in the mockup.

**002 — Case study deep dive.** Each case gets its own route (`/work/01-evals`), not an
in-page modal. A case can then be shared as a link, indexed, and translated, and "next case"
is just a link. The home cards link there.

**003 — Get in touch.** Email copies to the clipboard with an inline confirmation, and a
`mailto:` fallback works without JavaScript. The sticky bar appears on mobile only; on desktop
the nav button covers "one tap away". The CV downloads directly from `/cv/`, with no form.

**006 — Public profile export.** A small parser reads `profile.md` by heading and keeps only
an allow-list of fields: contact without the phone, roles, education, skills and languages.
Its output, `data/public-profile.json`, is **committed**, because CI cannot see
`cv-manager` (local, no remote) and must build from what is in the repository. The export
runs in Docker with `../cv-manager` mounted read-only.

## 4. Risks

| Risk | Impact | Mitigation |
| ---- | ------ | ---------- |
| A private field reaches the public repo (phone, salary, deal-breakers, HTML comments in `profile.md`) | High, and irreversible once pushed | Allow-list instead of deny-list; comments stripped; a test fails if the output contains a phone pattern, a currency amount or any allow-listed field outside its schema. |
| `profile.md` changes shape and the parser silently drops a role | Timeline out of date | The export validates against a schema and fails loudly; the diff of the committed JSON is reviewed like code. |
| Text contrast below AA | Fails the definition of done | Found during this analysis: `text/subtle` was 3.66–4.12:1. It is now `#80808A` (dark) and `#6B6B74` (light), and the light accents were darkened too. All text tokens clear 4.5:1 in both modes, and Figma is updated. Lighthouse CI keeps it that way. |
| The hero Ask prompt ships before the agent exists | A fake chat undermines the "honest" pitch | See decision 1. |
| Serif accent line reflows when the font loads | Layout shift on the headline, CLS penalty | Metric-matched fallback via `size-adjust`; preload Instrument Serif Italic only. |
| Aurora glow implemented with CSS `filter: blur()` | Janky scroll on low-end phones | A radial gradient on a static layer; no live filter. |
| GitHub Pages URL changes when a domain is bought | Broken links already sent to recruiters | Buy the domain before the first link goes out; Pages keeps redirecting the `github.io` address. |

## 5. Decisions

**✅ Decision 1 — What the hero prompt does in Phase 1.** Confirmed 2026-09-23: A. The agent is Phase 2, but the
prompt is in the approved hero.
- **A (recommended):** a ⌘K command palette. Typing filters the sections, cases and repos,
  and the three suggested questions jump to the case that answers them. It is honest and
  useful today, and in Phase 2 the same component gains an "Ask" mode backed by the agent.
- B: hide the prompt and the Ask section until Phase 2.
- C: pre-written answers presented as a chat. Not recommended — it is the one thing on the
  page that would not be what it claims.

**✅ Decision 2 — Case study visuals.** Confirmed 2026-09-23: static now, interactive in Phase 3. Story 002 asks for interactive visuals (slider,
falling line, draining queue, agent graph); the plan put that polish in Phase 3.
- **Recommended:** Phase 1 ships the static before → after panel from the mockup with a
  count-up on scroll; the four bespoke visuals land in Phase 3. Story 002 is amended to say
  so.

**✅ Decision 3 — Where the CV PDF comes from.** Confirmed 2026-09-23: generated from `/cv`. No PDF generator exists yet; the last PDF was
tailored for N26 and includes both phone numbers.
- **Recommended:** a print-styled `/cv` route rendered from the same public profile and
  printed to PDF by headless Chromium in Docker at build time, once per locale. The site and
  the PDF can then never disagree. Email, LinkedIn and GitHub only — no phone.
- Alternative: you keep curating PDFs by hand and drop them in `public/cv/`.

**✅ Decision 4 — Conversion tracking (story 003).** Confirmed 2026-09-23: events now, PostHog in Phase 4.
- **Recommended:** Phase 1 emits named events (`cv_download`, `email_copy`, `email_open`)
  through a small `track()` function that does nothing yet. Phase 4 connects it to PostHog
  EU in cookieless mode, which needs no consent banner. This keeps GDPR out of the launch
  path.
- Alternative: connect PostHog EU from day one.

**Adopted without confirmation:**
- Case studies on their own routes (002).
- `data/public-profile.json` committed, with the export run locally (006).
- Self-hosted fonts, Tailwind 4 tokens, no UI framework in Phase 1.
- i18n-ready routing and string tables from the first commit, with only `en` filled. Story
  004 then adds translations, not architecture.
